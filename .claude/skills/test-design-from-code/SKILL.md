> Stage 3 of 4 — `codebase-recon` → `behavior-spec` → **`test-design-from-code`** → `suite-export`. Nothing here is written to disk; Stage 4 renders it into one CSV and one report.

## Three properties every case must have

**Executable** — a new QA engineer given only the case can run it; every value they need is in it, nothing is "as appropriate". **Tester-executable through the API or the UI** — the person running this has a deployed system, an HTTP client and a browser, *not* the source, a harness, or a way to call a function. **Traceable** — cites a use case or rule, a surface, and the `path:line` proving the expected result; an untraceable expected result is an opinion. A case failing any of the three is not shipped, however sensible it looks.

## One suite, black-box layers only

**One case set per run holding every case in the scope**, which Stage 4 renders to a single CSV. The module is a **column on the traceability row** — never a folder, never a thirteenth case field (a `**Module:**` line is silently absorbed into the previous field and warned about). Every case has a `Module` value: an unattributed case is missing from every per-module total while still inflating the overall one. IDs stay module-prefixed (`TC-CHK-002`) and cases are grouped under `## {{Module}}` headings for the reader. A scope large enough to produce thousands of cases should have been split at Stage 1 — into two *runs*, not two files.

**Allowed layers: `API`, `UI`, `E2E`, `Contract`. `Unit` and `Component` are not layers in this suite.** A unit case asks the tester to check out the repo and wire a harness, which they will not do — so the row is skipped, and **a skipped row still counts as coverage in every total**: the rule reads as tested when nobody ever exercised it. So a deep rule is **pulled up, not tested down**:

**Rule enforced three hops below the entry point** → Drive it through the endpoint or screen whose request reaches it; evidence still cites the deep `path:line` · **Several endpoints reach the same deep rule** → Cover it through **each** where the observable outcome differs — that difference is the behaviour · **The effect is not observable in any response** → Assert it where it is: a persisted row, an emitted event, a later read through another endpoint. Name that oracle · ****Nothing reaches it at all**** → Coverage row `Unreachable-Black-Box` with the reason and `path:line`. **Never a unit case** — unreachable-from-outside is dead code or a missing surface, both worth more than a test QA cannot run
`Contract` stays allowed: a tester can validate a response against a schema with the HTTP client they already have. Stage 4 reports any other `Layer` value in Warnings.

## The case schema — exactly twelve fields, in order

`Test Case ID · Title · Objective · Preconditions · Test Data · Steps · Expected Result · Priority · Tags · Notes · Review · Automation`
Byte-identical to the Agentic AI Testing Platform Stage 3 schema, which is what makes this suite a drop-in. **Never invent a thirteenth field** — extras go in the report sections and the side tables below, which is where the CSV `Layer`, `Entry Point`, `Oracle`, `Source`, `Reason for Extraction` and run-provenance columns come from.

**ID** `TC-<MODULE>-<NNN>`, unique, **stable across re-runs**; retire, never reuse. **Title** short, specific, the behaviour not the mechanics. **Objective** ONE sentence, not a restatement of the requirement. **Preconditions** only what must be true immediately before step 1, not setup narrative. **Test Data** the values the steps actually reference, never values they do not; omit the field entirely when there is none. **Steps** ONE action per step, actions only — verification belongs in Expected Result ("Click Save and check the message" is two things). **Expected Result** the specific observable outcome constituting a pass: status/code, the value, the postcondition. **Priority** `P1`-`P4`. **Tags** exactly one granularity tier plus the test types. **Notes** genuinely useful context only, never a hiding place for a step or a value. **Review** and **Automation** are always literally `Pending` — they record **human** decisions taken after generation, and a skill that advances its own review status has reviewed its own work.
**Granularity tier, exactly one:** `Atomic` (one rule or validation — the default and most of the suite) · `Scenario` (one workflow of several rules that only make sense together) · `E2E` (a journey across surfaces; **additive, never replacing** the atomic cases over the same ground). One behaviour per case: chained unrelated actions get split; the same behaviour over several data points stays one case with several datasets. Before finalizing, check a new QA engineer could execute it unaided in under 30 seconds — **if removing a sentence does not change how the test is executed, remove it.**

## Workflow

Load the spec, inventory, gaps, existing tests and (below full-repo) the closure → **enumerate the flows** (section K) alongside the surfaces, a second denominator rather than a by-product → build the **evaluation grid**: every surface × every test type below, `EXT` boundaries and section J included, plus every flow × every K row → per cell generate the case(s) or record `Not Applicable — {one-line reason}`; **a cell is never blank** → derive test data mechanically → write the execution profile (isolation is mandatory) → write traceability including `Module` → assemble the one scope-wide case set → write the coverage report with both denominators → self-check, then hand off.

## The coverage engine — evaluate every type, per surface

Written in HTTP vocabulary; a type is **never** `Not Applicable` merely because the surface has no HTTP request — use the per-shape equivalent below.
**A. Functional** — A1 happy path (always) · A2 alternate flow (per alternate in the use case) · A3 business rule direct, exercised head-on not incidentally (per `BR-`) · A4 calculation accuracy incl. rounding (per `Calculation` rule) · A5 default applied (per field with a default: omit it, assert the default) · A6 optional omitted.
**B. Input validation, derived mechanically from Data Contracts** — B1 required missing · B2 empty/whitespace-only (strings) · B3 null where non-null · B4 wrong type (always) · B5 **boundary set: four values** min−1, min, max, max+1 · B6 pattern violation (one near-miss, not gibberish) · B7 enum violation plus a case-variant · B8 oversized payload/array/file · B9 unicode (accented Latin, CJK, RTL, emoji) · B10 format-significant characters, always (`<script>`, `&`, quotes, backslashes; unescaped quotes/newlines for JSON; delimiters for CSV) · B11 uniqueness violation · B12 referential violation (nonexistent parent).
**C. AuthN/AuthZ** — C1 unauthenticated · C2 wrong role, **one case per role boundary** not one generic case · C3 ownership violation (valid role, another user's record) · C4 invalid/expired/malformed credential · C5 mass assignment (`role`, `isAdmin`, `price`) · C6 rate limit · C7 injection-shaped input, always, as an **input-handling and error-message probe only** — assert safe rejection and that no internal detail leaks, never to exploit.
**D. State and lifecycle** — D1 legal transition (per edge) · D2 illegal transition (per non-edge, or a representative set stated as such) · D3 idempotency (repeat the identical mutation) · D4 concurrency (simultaneous mutation of one record) · D5 ordering dependence.
**E. Error handling and resilience** — E1 error response shape per distinct error: status, code and shape, not "an error" · E2 **boundary failure, one case per mode**, never one case for "the dependency fails" · E2b boundary success through the caller · E3 timeout · E4 rollback on partial failure.
**F. Data and persistence** — F1 persistence assertion (assert stored state, not only the response) · F2 cascade/soft-delete · F3 DB-applied default · F4 migration consistency, up and where supported down.
**G. Contract** — G1 response schema conformance · G2 backward compatibility (versioned or publicly consumed) · G3 event/message payload contract.
**H. UI surfaces** — H1 initial render/default state · H2 client/server validation parity (assert the server enforces it too) · H3 empty/loading/error states, one case each · H4 accessibility: labels, roles, keyboard reachability, focus order, contrast · H5 responsive (per breakpoint) · H6 i18n: externalized strings, locale number/date formats, RTL.
**I. Cross-cutting** — I1 configuration state, **one case per documented state**, never an invented one · I2 integration of two rules, testing the *interaction* · I3 observability/audit event emitted · I4 pagination/sorting/filtering: defaults, limits, out-of-range page, invalid sort key · I5 performance-sensitive path — assert the bound (N+1, unbounded query, documented budget), not a wall-clock number · I6 regression asserting the **corrected** behaviour, never a restatement of the bug · I7 E2E journey (see K) · I8 smoke tag on the minimal set proving the module is alive.
**J. Execution depth (scope narrower than the repo), from the closure** — J1 deep rule through its shallowest entry point, one case per entry point that handles it differently; where none reaches it, a coverage row not a case · J2 full-path integration per use case spanning ≥2 internal layers · J3 conflicting constraints across layers — one case at the tighter limit, proving which governs · J4 duplicated enforcement, one case per enforcement point · J5 impacted-caller regression, one per impacted entry point · J6 unreached-code probe: record as uncovered rather than generating a case that cannot be driven.
**K. Flows and journeys — not optional, not a garnish.** A suite of 300 atomic cases with no journey has never exercised the system the way it is used. **Enumerate flows first**: each `UC-` touching more than one surface; each state-machine path from initial to each terminal state; each UI route sequence; each create→read→update→delete cycle; each path crossing backend and frontend. Then per flow: K1 primary happy journey, asserting the outcome **and** the state left behind at each surface · K2 alternate journey per legitimate variation, one case each not one with branches · K3 journey interrupted mid-flow (≥2 mutating steps): abandon after step *n*, assert what persists and what does not — this is where half-written state lives · K4 resume/re-entry, assert nothing lost or double-applied · K5 backward navigation and re-submission, assert no duplicate record and no stale value · K6 cross-surface data consistency · K7 cross-role journey across the handover · K8 failure-recovery journey through an `EXT` boundary: fail mid-journey, retry, complete — assert no double charge and no orphan record · K9 full entity lifecycle through every legal state, then confirm it is gone from every surface that listed it · K10 backend/frontend contract in the journey, including the error path surfacing to the user.
Journeys are **additive**: a K case never replaces atomic cases. A failing journey says *that* the flow broke; the atomic case says *which* rule broke. Write each journey as one case with numbered steps across surfaces, one Expected Result naming the final state plus each intermediate assertion, and an `Entry Point` naming the sequence (`POST /api/cart → POST /api/checkout → GET /api/orders/:id`). **Report flows enumerated / flows covered beside the surface percentage** — 100% of surfaces with 20% of flows is not a covered system.

**Per-shape equivalents** — required/empty: omitted property, blank required field, missing envelope field, missing column, missing flag · boundary: numeric/length bound, input maxlength, max message size, max rows, max argument length · wrong type: wrong JSON type or `Content-Type`, text in a number input, schema-violating payload, wrong column type · unicode/special chars: multi-byte values, rendered output, CSV delimiters and quotes, shell-significant characters · authN/authZ: unauthenticated, route guard, hidden-but-reachable control, forbidden topic, wrong principal, missing permission · timeout: slow upstream, loading and error state, unacknowledged/redelivered/poison message, job over its window, interrupted command · idempotency: repeated POST, double-click submit, duplicate delivery, job re-run, command re-run · concurrency: simultaneous writes, two tabs, two consumers on one partition, overlapping runs.
`Not Applicable — {reason}` goes in the grid. Legitimate: "surface is read-only, no state to transition". Not legitimate: "not relevant", "N/A", or silence.

### Covering an unreadable dependency

"Simulate a failure from the payment provider" names no failure, no injection point and no expected result — nobody can execute it. Everything needed is already in the closure data and Stage 2: **which failure** from the boundary role mode list (`declined`, `unique-violation`, `http-5xx`) · **where to inject it**, the call site `path:line` · **what is expected**, from the caller error handling Stage 2 read · **which layer**, `API` or `UI` — whichever entry point reaches the call site, the boundary controlled through what the tester has (sandbox mode, stub upstream, seeded failure fixture); never `Component` · **isolation** from the closure (a shared sandbox is `exclusive`).
**Arithmetic:** one success case plus one case per failure mode, **per calling surface** — two surfaces calling one gateway usually handle a decline differently. A service with six unreadable dependencies typically yields thirty-plus cases. A mode is genuinely N/A only when the code path cannot produce it (a read-only query cannot hit a uniqueness violation), it is prevented upstream, or the boundary is not on this surface path. **Not valid:** hard to arrange, no sandbox, assumed reliable — those are execution problems belonging in Automation Notes, and recording them as N/A converts a missing test into a false coverage claim.
**Assert the caller, never the dependency.** "Stripe returns a 402" is a precondition; the expected result is the status the caller returns, the error code, whether the order row exists, whether stock was released, whether the retry happened. Where Stage 2 found **no handling**, assert the behaviour that actually occurs — a 500, a leaked message, a half-written record — with a note naming the gap. A test asserting the sensible behaviour the code does not implement fails on unchanged code and gets deleted.

## Test data, derived mechanically

Every value comes from a constraint in Data Contracts; **never invent one where the code states it**.

`1 ≤ n ≤ 99` → `0`, `1`, `99`, `100` (Boundary-Below/Min/Max/Above) · `n > 0` exclusive → `0`, `1`, `-1` (Boundary-Below, Boundary-Min, Invalid-Range) · `maxLength 120` → `""`, 1 char, 120, 121 (Empty, Boundary-Min/Max/Above) · `^[A-Z0-9]{4,12}$` → `SPRING10`, `spring10`, `ABC`, `A@BC` (Valid, Invalid-Format ×3) · enum `{pending,paid,shipped}` → each member, `refunded`, `PENDING` (Valid ×3, Invalid-Enum, Invalid-Case) · required / non-nullable / unique → present+absent · value+`null` · fresh+existing (Valid, Empty / Null / Duplicate) · foreign key → existing parent id, well-formed nonexistent (Valid, Invalid-Reference) · date/time ordering rule → satisfying, violating, the exact boundary instant (Valid, Expired, Boundary-Max) · free text → ASCII, `Ünïcödé 中文 🎉`, `<script>alert(1)</script>` (Valid, Unicode, SpecialChars) · **no constraint found** → one ordinary value, one extreme (very long, control chars) (Valid, Unconstrained-Probe — cite the gap)

**Inclusivity decides the values:** `≤ 99` gives max 99 and above 100; `< 99` gives 98 and 99. Read Stage 2's interval literally; ambiguity is a gap, not a guess. **Concrete, never a description** — `SPRING10` not "a valid promo code", `2025-01-31T23:59:59Z` not "a past date". Relative dates are stated as a rule (`expiresAt = now − 1 day`) with the format, since a hardcoded past date becomes a different kind of past over two years. **No real personal data, ever**, even if the repo has a seed file of real-looking records. Injection probes are inert: a string that *looks* like an attack, asserted to be rejected safely.
**Test Data table** — one row per **field**, not per dataset: `| Dataset ID | Test Case ID | Purpose | Field | Value | Value Kind | Source Evidence |`. Every row cites the constraint it came from, so a reviewer can open the line and confirm the boundary. One behaviour across several data points is **one case with several datasets**; split into separate cases only when the *expected result differs* (`99 → accepted` and `100 → rejected` are two behaviours).

## Execution profile and the parallel plan

`| Test Case ID | Layer | Entry Point | Oracle | Fixtures | Teardown | Isolation | Parallel Group | Deterministic | Est. Runtime | Automation Notes |`
**Layer** `API`/`UI`/`Contract`/`E2E` and nothing else — pick the cheapest of the four that observes the behaviour (a DTO rule reachable through one endpoint is `API`, not `E2E`; spending 40 seconds to assert one validation message buys nothing). Depth in the closure changes the entry point, never the layer. **Entry Point** exactly how the case is addressed. **Oracle** how pass is decided: `HTTPStatus`/`JSONBody`/`SchemaMatch`/`DBState`/`EventEmitted`/`LogEntry`/`UIAssertion`/`Snapshot`, combined with `+`. **Fixtures** named (`seed:promo-spring10`) so a runner can share them. **Teardown** what must be undone, or `none`. **Parallel Group** usually blank, derived from isolation. **Deterministic** `Yes`/`No`, with a reason in Automation Notes for `No`. **Est. Runtime** an order of magnitude, to balance shards.
**Isolation is mandatory**, from this closed vocabulary: `read-only` (fully parallel) · `shared-fixture:<name>` (parallel within group) · `mutates-record:<entity>` (parallel within group) · `exclusive:<resource>` (serialized on it — a payment sandbox, a single test account, a rate-limit budget) · `global-state` (runs alone: a flag, the clock, global config). **Choose the strictest level that is true, not the loosest that seems plausible.** An absent or unrecognised value is scheduled `exclusive`, the safe direction; marking everything `read-only` for parallelism buys speed with intermittent failures that cost far more than the serial run avoided.

## Traceability, priority, coverage

`| Test Case ID | Module | Use Case ID | Business Rule ID | Surface ID | Requirement / Source | Source Evidence | Risk | Confidence |` — **every case has a row**, `Module` mandatory (carried here because the twelve fields are fixed). Source Evidence is the line proving the *expected result*, not merely where the surface lives. Confidence is inherited from the weakest rule the case rests on, and an assumption-derived case names its gap in Notes. Risk `Low`/`Medium`/`High`/`Critical` from blast radius: money, data loss, auth, personal data, irreversibility.

## Provenance — where each case came from

`| Test Case ID | Source | Reason for Extraction |` — **every case has a row**, and Stage 4 renders these as CSV columns.
**Source** the `path:line` the case derives from, the same evidence as its traceability row (several separated by `;`), or `Assumption: <gap ID>` when no code backs it — the two must agree, because a Source the report does not corroborate is two claims that can disagree. **Reason for Extraction** the one clause naming *what made this case necessary*: the rule, boundary, failure mode, contract or journey (`Boundary: quantity max 99, upper-inclusive`, `EXT failure mode: gateway timeout`, `Contract: response schema OrderCreated`, `Journey K3: cart → checkout → order lookup`). It is **not** a restatement of the Objective: the Objective says what the case asserts, this says which cell of the evaluation grid demanded it — so a case whose reason cannot be written is a case nobody chose deliberately, and it should be dropped or traced properly rather than given a filler reason.

**Run provenance**, recorded once for the run and carried onto every CSV row by Stage 4: the exact **Claude model ID** that generated the suite, the **effort level** the run used, and the **verbatim user prompt** that initiated it. Record them as observed, never from memory or inference; where a value genuinely cannot be determined, write `Unknown` so Stage 4 warns instead of publishing an invented one. They are identical on every row of one run by design — that is what lets a merged or filtered CSV still say which run produced which case.
Priority follows risk, not set independently: `P1` critical/high-risk happy paths, auth boundaries, money, data integrity (the smoke set) · `P2` core rules, primary negatives, main error handling · `P3` secondary validation, boundary sweep, alternate flows · `P4` cosmetic, rare configs, low-risk edges. **A High or Critical requirement is never left with only a `P4` case** — if every case for it is P3+, the design is wrong.
**Coverage report** — per-item status first: `| Item ID | Item Type | Status | Test Case IDs | Reason | Source Evidence |`, where status is `Covered` (≥1 case and every applicable type generated) · `Partially Covered` · `Uncovered` (in scope, assessable, zero cases, no reason — always a defect in this stage's own output) · `Out-of-Scope` · `Unknown` (the behaviour itself is a gap) · `Unreachable-Black-Box` (evidenced but no surface reaches it: cite `path:line` and say what would have to exist to test it). **The percentage is computed against `Covered` only**, the others reported beside it, never folded in.
Then, in order: Scope · Execution Closure · Surfaces Covered · Flow Coverage · Boundary Coverage · Evaluation Grid (surface × type and flow × K, with every `Not Applicable` reason) · Business Rules · Case Counts by Module and Type · Unreachable-Black-Box Items · Assumption-Derived Cases · Coverage Gaps · Risks · Parallel Plan Summary · Review & Automation Roll-up · Handoff Checklist. **Two denominators side by side, always:** surfaces with ≥1 case and every type evaluated, and flows with a K1 case and K2-K10 evaluated. For a sub-scope run also state seed vs reached files and depth walked · closure files with no case and why · per boundary, modes covered / possible · impacted callers and whether each has a regression case · unresolved edges (behaviour beyond them is `Unknown`) · what a truncation removes from the claim. The evaluation grid is the completeness argument; without it "we covered everything" is unfalsifiable.

## Self-check before handing off

Twelve fields in order with no invented labels · exactly one tier tag · a traceability row with `path:line` and a `Module` · an execution-profile row with a valid isolation · a provenance row whose `Source` matches its traceability evidence and whose `Reason for Extraction` names a rule, boundary, mode, contract or journey · run provenance recorded once as observed, `Unknown` rather than guessed · every value concrete · every boundary set has four values with inclusivity read from the constraint · one authorization case per role boundary, ownership tested separately · every distinct error outcome asserts status **and** code · every grid cell generated or `Not Applicable — reason` · every assumption-derived case names its gap · `Review` and `Automation` literally `Pending` · no case duplicates an existing test without saying why · every `EXT` boundary has one case per failure mode or `Not Applicable` **per mode** with a valid reason · boundary cases assert the caller · every `Layer` is `API`/`UI`/`E2E`/`Contract` · every deep rule driven through a reaching entry point or recorded `Unreachable-Black-Box`, never given a unit case · ONE case set grouped under `## {{Module}}` headings · every impacted caller has a regression case or a stated reason · section J evaluated for every multi-layer closure · coverage states seed vs reached, boundary modes covered/possible, and any truncation · every `suite-export` check passes or is recorded as a warning.
**Never:** "enter an invalid email" (which one?) · one case per endpoint (nine behaviours, one case, reported 100%) · a boundary case with only max and max+1 · chaining unrelated actions · an E2E case replacing atomic ones · verification inside a step · restating the bug as the expected result · inventing a config value the code does not define · `Review: Approved` · hand-editing the generated CSV (it is regenerated silently) · one CSV per module · a suite of atomic cases with no journeys · one E2E case with branches per variation.
